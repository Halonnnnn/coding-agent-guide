# Coding Agent 开发实践指南

## 核心判断：复杂度应与问题规模匹配

当前主流工具已经内置了harness、sandbox、loop、渐进式披露和上下文管理等机制，使用者的主要工作是把任务切清楚、把项目知识整理好、把验证做好。**复杂的 Agent 框架并非没有价值，但学习成本和维护成本可能会很高。如果在没有遇到实际瓶颈时就引入复杂的agent框架，多数情况下投入会超过收益**。就像Java 开发中也有类似的取舍：单体服务即使可以使用分布式锁，多数业务场景用 `synchronized`、`ReentrantLock` 或 CAS（乐观锁）已经足够，而且更容易理解和维护。

因此，**本文建议先用最简单的方式开始，等遇到具体、可观察的瓶颈，再引入更复杂的机制**。

另一条总纲同样值得前置：**AI 编程的成熟度应该用判断力衡量，而不是创造力**——知道怎么挖掘和识别代码、什么时候应该写代码，什么时候应该复用代码，什么时候根本不应该写代码，达到用户共识。在已有系统中，AI 应该首先扮演遵循既有系统规则的工程师，而不是试图重新设计系统的架构师。展开原则见 [4.11](04-改进机制/4.11-模仿优先创造和猜测受控.md)"模仿优先，创造和猜测受控"。

在方法层面，本文认为目前 AI 辅助软件开发最佳的工程化方法是 **Harness + SDD**：

- **Harness（开发框架 / 执行环境）**：给 AI Agent 设置工作环境、工具、权限、规则和测试机制，让 AI 能可靠地执行开发任务。本文的项目知识（[4.3](04-改进机制/4.03-项目知识分三层管理.md)）、验证机制（[4.6](04-改进机制/4.06-基于证据的验证与完成状态.md)）、Review 约束（[4.7](04-改进机制/4.07-代码Review.md)）与安全红线（[4.9](04-改进机制/4.09-安全红线与执行约束.md)）都属于 Harness 层。
- **SDD（Spec-Driven Development，规范驱动开发）**：先写清楚需求、规格、验收标准，再让 AI 根据规格编写代码，而不是直接让 AI 凭一句话生成代码。本文的任务卡（[4.2](04-改进机制/4.02-任务卡.md)）与[第五节](05-落地路径/README.md)的五阶段工作流（调研→设计→实施→验证→归档）是其落地形式。

两者分工明确：Harness 解决"能否可靠执行"，SDD 解决"执行方向是否正确"，遵循“搜得到”与“讲得清”的准线。这与"复杂度应与问题规模匹配"并不冲突——Harness 强调的是配置好现有工具的环境、规则与验证，而不是另建一套复杂的 Agent 框架。

**特别注意：本文不会细化展开 agent 框架的搭建。**
