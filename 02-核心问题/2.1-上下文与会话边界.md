# 2.1 上下文与会话边界

**上下文容量不等于有效工作能力。** 多个任务混在同一会话中时，不同任务的约束和假设会互相串扰：历史需求干扰当前需求，已经失效的假设仍在影响决策。即使上下文占用率不高，Agent 的修改范围也可能扩大、质量也可能下降。例如开发中曾观察到，上下文使用率约 41%（在百万上下文容量的基础上）时，混入长任务执行、功能追加和 Bug 修复等多个任务的会话已经出现质量波动：Agent 把前一个任务的约束套用到当前任务上，修改范围超出本次需求。<!--这一数值仅是特定项目的观察，不能作为通用切换阈值-->因此，应该合理地切分会话边界，比如依据任务边界划分。

**错误结论比上下文长度更危险，即：“上下文腐败”。** 会话中的失败尝试、未经验证的解释和错误的中间结论，会被 Agent 当作经验在后续推理中反复引用：沿用已经不成立的判断，或者把失败尝试当作排除依据却没有核实原因。例如多次 Bug 修复中，旧会话快速完成但质量较差，新会话花了几倍的时间和 tok 重新分析后结果明显更好。旧会话的问题在于它带着错误判断继续工作；新会话的优势来自重新核实了事实，而不是新会话本身更可靠。上下文腐败的案例以及表现不止于此，这里不再展开。
