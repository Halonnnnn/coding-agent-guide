# 2.2 需求映射与项目知识

**自然语言需求往往无法唯一对应到代码对象。** “接口”“方法”这类边界明确的对象容易定位，但“调整卡片”“优化接口”“看一下”“分析一下”这类表达（归类为：动作意图指令）可能有多种解释。比如调整卡片可能指容器、图片、标题、样式或交互逻辑中的任何一个，优化接口可能指响应时间、参数设计、异常处理或兼容性。结果往往是识别错了对象，或者只改了表面现象。

**业务术语不能靠字面推断。** 例如要统计“举手率”，Agent 并不知道“举手”在业务中指什么、由哪个事件触发、分子分母如何定义，只能凭字面猜测。这类术语必须先在项目知识中给出明确定义，否则统计结果看似正常，口径却可能完全错误。

**服务多了以后，找到正确的服务本身就是成本。** 传统互联网项目可能会有十几个、几十个乃至上百个的服务，职责相互交叉。如果没有服务地图（即业务本体、serverMap），大模型往往会显得不够聪明。比如：处理“下单”相关问题时，Agent 可以凭服务名 `order` 很快定位；但如果服务名是 `Poseidon`，就只能在大量代码中反复探索，既消耗 Token，也容易找错。服务地图记录每个服务的职责、边界和入口，让 Agent 先定位再深入——这本身也是渐进式披露的一种体现：不必一次加载全部代码，而是按需进入相关服务。

**项目知识没有转化为可查询、可验证的显式知识。** 业务规则、架构设计、模块职责和历史决策如果只存在于开发者经验或历史聊天记录中，Agent 就无法在任务和会话之间稳定复用。表现为同一个规则需要反复解释、不同任务对同一模块形成不一致的理解、相似功能被重复实现。单纯增加会话历史无法替代项目知识管理。

**文档的可信度没有被按事实域区分。** Agent 倾向于把检索到的文档当作均匀可信：既会引用过期内容，也会超出文档的权威范围使用它。例如官方 API 文档对参数定义是权威，对接口当前运行状态却不是——Agent 不会区分“这份文档有资格回答什么”，于是把文档描述当作运行时事实，或在文档与实际行为冲突时继续相信文档（[2.3](2.3-纠错补丁累积与架构一致性.md) 的 `timeout_express` 案例中，修补多轮才暴露根因，正是文档与沙箱行为不一致）。这类问题不能靠“多查几份文档”解决，需要预先定义信任边界，见 [4.3](../04-改进机制/4.03-项目知识分三层管理.md) 的上下文可信度与治理机制。

**需要澄清的是**：引入业务本体和 serverMap 并不必然节省 tok 和时间，由于 Agent 框架复杂度上升，消耗可能不减反增。它们的价值是让大模型在业务中发挥实力，更准更稳，而不是省耗。
