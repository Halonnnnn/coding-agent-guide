# 2.3 纠错、补丁累积与架构一致性

**理解纠错指令，不等于纠正了错误的分析路径。** Agent 通常围绕最近一次指令做局部优化：只修了表面现象，没有解决根本原因；在已经被否定的方案上继续叠加补丁；同一个问题经过多轮修改仍然反复出现。例如在某次支付宝充值接入中，订单超时参数 `timeout_express=5m` 在沙箱中并未生效，超过 5 分钟后订单仍然可以支付。之后陆续提出了主动关闭订单、状态轮询、倒计时归零等方案，都因为增加复杂度而被否决。但问题的根因是支付宝对该字段的行为与文档不一致，始终没有被正面解决——每一轮修补都是在“让本地倒计时生效”这个已被证明走不通的方向上叠加。

**多轮迭代容易退化为补丁式开发。** 特殊判断和条件分支不断增加，同一个模块被反复修改，修一个 Bug 又引入另一个，相同的逻辑在多处重复实现。缺少架构约束和回归测试时，复杂度和缺陷风险会持续上升。例如某项目订单的 Extra 字段经历了四轮演化：先是独立列，再改为 JSON 字段，再补入补单标记，最后由诊断接口读取。每一步单独看都合理，但兼容层越来越多，数据结构越来越绕，弃用的列仍然留在数据库中（GORM 不会自动删除），始终没有人从头重新设计。

**局部可行的方案未必符合整体设计。** 修改一个公共组件可能会影响多个页面；在后端，类似的问题表现为绕过统一的服务层，或者修改了接口却遗漏了调用方，导致接口定义、类型声明和测试之间出现不一致。例如某项目诊断信息展示方式迭代了三次：第一版让 root 用户和普通用户看到相同的占位提示，被否决；第二版给 root 额外加了一个诊断按钮，同样被否决。最终方案是把诊断信息放到独立的只读 root 路由中，不写入订单状态，入口与普通用户的提示完全分离。前两版在“让 root 看到更多信息”这个局部目标上都可行，但都违反了“诊断与状态修改必须分离”的整体原则。
