# 4.6 基于证据的验证与完成状态【建议】

代码生成完成、构建通过、测试通过和业务验收通过，是四个不同层次的结果。应当根据任务的风险和修改范围，设置对应的验证机制。

- **代码层**：查看实际差异，确认没有不必要的文件修改；检查关键逻辑、异常处理和边界条件；确认接口、类型定义和调用方保持一致。代码差异是判断 Agent 实际做了什么的依据，不能只看它的文字总结。
- **自动化验证**：根据任务类型选择单元测试、集成测试、静态与类型检查、项目构建、接口契约测试，以及异常输入和失败分支的验证。如果项目还没有相应的测试，不能把测试缺失视为通过，而应当说明当前验证的范围和未覆盖的风险。
- **视觉验收**：适用于布局、样式和交互修改。应当确认验收的页面、设备和环境，对比修改前后的截图，检查相关页面和公共组件是否回归，并通过实际操作验证关键交互。
- **运行环境**：对依赖线上或测试环境的任务，应当查询授权范围内的部署记录、日志和监控，核对实际部署版本、服务状态和发生时间。如果 Agent 没有相应权限，应当明确说明限制，并把需要人工确认的内容列为待验证事项。

完成状态分为四级，任务记录中必须标明：**实现完成**（代码修改已完成）、**检查完成**（已执行审查、测试或构建）、**验收完成**（约定的关键行为和结果已确认）、**存在未验证事项**（部分环境、边界或外部依赖尚未确认，并列出具体内容）。

任务结束后，除了沉淀经验，还可以让 Agent 对本次任务的执行过程做一次结构化评分，从多个维度进行评估，例如对项目规则和指令的遵守程度、需求理解是否准确、修改范围是否受控、提示词本身的专业度与清晰度，以及验证是否充分。评分的价值在于把“这次做得怎么样”转化为可以比较的记录，便于发现哪类指令经常被忽略、哪类任务反复出问题，从而有针对性地修订规则文件或任务卡模板。

需要注意的是，Agent 给自己打分容易偏向乐观，因此评分维度应当预先定义，并尽量对应可检查的事实，例如是否改动了禁止修改的文件、是否执行了约定的测试，而不能只凭主观感受。评分结果适合作为改进规则的参考，不宜作为衡量 Agent 能力的绝对指标，也不能替代本节的基于证据的验证。

Claude Code 提供了 `/insights` 命令，可以基于近期的本地会话生成一份 HTML 分析报告，内容包括项目分布、使用习惯、反复出现的问题，并给出 CLAUDE.md、Skills、Hooks 等配置方面的建议。它不是对单个任务的评分，但适合用来发现跨任务的共性问题，例如同一类指令被反复忽略，或某类任务总是需要多轮返工。该命令的具体内容和可用性随版本变化，使用前应以官方文档为准。
