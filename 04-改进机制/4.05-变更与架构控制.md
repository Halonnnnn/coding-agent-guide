# 4.5 变更与架构控制【建议】

**修改之前**：涉及多个文件、公共组件、接口或数据结构的任务，要先弄清楚三件事：直接修改的对象及其职责，相关的调用方和依赖模块，以及必须保持不变的行为和对应的验收范围。简单任务不必做冗长的分析，但公共模块、跨服务接口和高风险变更要先完成影响分析。

**修改过程中**：修改共享组件或服务接口时，应当遵循既有架构，不要为了快速解决局部问题而引入重复逻辑或特殊判断；代码生成的具体原则见 [4.11](4.11-模仿优先创造和猜测受控.md)。如果现有架构本身存在问题，应当把架构调整作为单独的任务来评估，而不是在局部需求中顺手做大范围重构。

**变更单元**：每个任务应当形成独立、可审查的变更单元，记录任务目标与修改范围、实际修改的文件、关键设计取舍、测试和验收结果、未解决问题以及回滚方式。使用 Git 的项目可以借助分支和提交来实现这一点。多人或多个 Agent 共同修改时，应当明确共享文件的修改责任和合并顺序。
