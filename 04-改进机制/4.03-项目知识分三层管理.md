# 4.3 项目知识分三层管理【建议】

项目知识不能只留在对话记录里，而应当按性质分层存放。三层的更新频率和可信度要求各不相同，因此需要分开管理：

- **项目级知识**（架构约束、业务规则、编码规范、模块职责）：写入项目文档并持续维护。
- **任务级状态**（目标、修改范围、已验证结论、待办事项）：随任务推进及时更新。
- **临时过程信息**（调试输出、失败尝试、短期假设）：仅在当前任务需要时保留，不进入长期知识库。

其中，对象映射是对 Agent 定位准确性影响最直接的一类知识。它需要为关键的 UI 组件或业务对象记录：业务含义、页面位置、组件标识或名称、源码路径、允许调整的内容和禁止改变的行为，以及验收方式。以"订单摘要卡"为例，映射应当能说明它对应哪个页面和哪段源码，并明确本次是只调整展示结构，还是同时涉及字段和交互。这样 Agent 才不会仅凭"卡片"两个字就选错组件。

除了对象映射之外，业务术语也需要明确定义。同一个词在不同服务中可能指向不同的含义，例如"订单"在交易服务和履约服务中的定义就可能不一样。术语表应当注明定义、适用范围和对应的代码字段。存在争议或尚未确认的规则，标注为"待确认"，避免 Agent 自行补全。

不过，文档本身也可能过时。执行修改之前，仍然需要核对文档与当前实现是否一致。过期的路径、错误的约束或相互冲突的文档，反而会成为新的错误来源。已有成熟文档体系的项目，应当沿用既有约定，不要为了适配 Agent 而重复建设文档体系。

**上下文可信度与治理机制（参考）**：不要让 Agent 自行决定是否相信一份文档，而应通过 Context Governance 机制，预先规定文档在什么条件下、针对什么事实可以被信任。**文档的可信度不等于文档内容的可信度**：一份官方 API 文档可能在 API 参数定义上具有最高权威性，但在 API 当前运行状态上没有权威性——后者只能来自运行时验证（[2.3](../02-核心问题/2.3-纠错补丁累积与架构一致性.md) 的 `timeout_express` 案例正是文档与实际行为冲突的实例）。落地形态是分层架构 + 分级信任策略 + 冲突处理规则：Prompt 定义原则，Metadata 提供依据，Policy 决定使用方式，Runtime Validation 保证执行安全。策略模板见 [6.7](../06-模板/6.7-Context治理策略模板.md)。
