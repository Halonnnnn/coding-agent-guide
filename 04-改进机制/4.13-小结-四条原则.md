# 4.13 小结：四条原则

以上几节可以归纳为四条原则。这些原则是我们基于三个项目的实践归纳出来的，适用于以业务知识为核心的 Agent，并不是已经被广泛验证的行业标准。开篇的"复杂度应与问题规模匹配"是总原则，这四条原则则是它在知识、架构、使用规范和治理四个层面的展开。

**第一条是知识分层要严格。**[4.3](4.03-项目知识分三层管理.md) 节把项目知识分为三层，其中能够自足判定的知识（如字段含义、状态码、接口约定）与需要结合上下文理解的叙事知识（如某个功能为什么这样设计、历史上做过哪些取舍）必须分开存放。如果两者混在一起，Agent 会把一段过时的叙事当作确定事实使用，这正是前文提到的文档过时问题的主要来源。

**第二条是基础设施要克制。**[3.2](../03-架构背景/3.2-单Agent与多Agent的选择.md) 节的判断表说明，多 Agent 体系会带来额外的协调、上下文同步和调试成本。对于大多数低频需求，单 Agent 加 Tool 已经足够，只有当单个 Agent 的上下文确实无法容纳任务，或者子任务之间确实需要独立的执行环境时，才值得引入更复杂的结构。Go 网关的迭代经验表明，过早地搭建复杂系统，往往会让问题的定位变得更困难。

**第三条是 Agent 使用规范要明确。**Agent 需要知道三件事：应该先查哪一层的知识，用什么方式查找，以及在什么条件下需要继续追溯到原始代码或文档。如果这些规则没有写清楚，Agent 要么频繁地全量读取，浪费上下文；要么在信息不足时凭经验推断，给出看似合理的错误结论。[4.2](4.02-任务卡.md) 节的任务卡和 [4.3](4.03-项目知识分三层管理.md) 节的对象映射，都是为了让这些规则落到具体的任务上。

**第四条是治理成本要与知识规模匹配。**知识的维护、核验、同步和监控都需要人力投入，而这些成本通常随知识规模线性甚至超线性增长。在 [4.10](4.10-成本评估.md) 节的成本评估中，我们建议先估算知识的更新频率和使用频率，再决定治理的强度。一个只有几十条字段说明、很少变动的项目，不需要为它建设完整的知识治理流程；而一个跨多个服务、多人维护的业务系统，则需要更严格的核验和同步机制。

可以概括为一句话：**让知识以适合其性质的形式存储，让 Agent 以明确的方式使用它，让基础设施只承担必要的复杂度，让治理投入始终与实际业务价值相匹配。**
