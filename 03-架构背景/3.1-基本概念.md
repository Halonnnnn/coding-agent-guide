# 3.1 基本概念

传统软件的执行步骤由开发者预先写死，程序只是按部就班地运行。Agent 则不同——它把“下一步做什么”的决定权交给了模型。在理解架构差异之前，需要先掌握三个相互关联的概念。

**Loop/workflow** 是 Agent 的基本运行方式。每一轮中，模型读取当前上下文，输出一个动作——调用某个工具，或者给出最终回答。工具的执行结果被写回上下文，模型再基于新的信息进入下一轮，直到判断任务完成。也就是说，“下一步”不是由流程图决定的，而是由模型在每一轮根据已有信息判断出来的。

**渐进式披露（Progressive Disclosure）**针对的是上下文容量有限的问题。内容越多，关键信息越容易被淹没。因此，Agent 不会把所有规则、知识和操作说明一次性放入上下文，而是等到相关时才加载。例如，某个 Skill 的详细说明只在任务需要时才进入上下文。这样，一个 Agent 才能具备较多能力，又不会互相干扰。

**共享上下文** 是 Loop/workflow 带来的直接结果。由于每次工具执行的结果都写回同一份上下文，模型所有的判断都基于同一份历史，这保证了决策的一致性。但代价也很明显：信息会持续累积，早期的错误假设也会一直留在上下文中。这正是后面讨论多 Agent 设计的出发点——把任务拆给多个 Agent，就意味着每个 Agent 只能看到部分上下文，共享与隔离之间需要取舍。

由此可以区分三种架构形态。如果任务不需要调用外部工具，单个模型直接推理和输出即可，这就是**单 Agent 架构**。如果任务需要调用外部能力，但所有决策都需要基于同一份完整信息，那么由一个决策者在 Loop/workflow 中调用多个工具即可，这就是**单 Agent 多 Tools 架构**。只有当子任务需要独立的上下文，或者需要多个独立视角来判断时，才需要引入多个决策者，即**多 Agent 架构**。
