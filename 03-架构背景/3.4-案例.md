# 3.4 案例

**支付宝官方支付功能开发**，适合单 Agent 多 Tools。流程为理解需求、拆分任务、阅读代码、编写代码、测试与审查、提交结果，步骤之间强依赖。适合的形态是一个 Agent Loop 加一组工具和检查点（Checkpoint），Skill、Rules、Memory 按需加载。

**分析没有成单的原因**，用单 Agent 加工具即可完成。问题涉及预估、发单、举手、派单等多个业务领域，但它们服务于同一个问题，Agent 依次查询各领域的数据，再综合判断即可。只有当数据量大到单个会话无法容纳时，才考虑把各领域的材料交给 subagent（Subagent-as-Tool）分别整理，再由 main-agent 综合决策。

**分析每个服务的架构，生成业务本体**，先由单 Agent 逐个服务分批完成。服务数量不多、单个服务代码量可控时，一个会话即可完成。只有服务多到单会话装不下，并且各服务之间确实相互独立时，才考虑并行的多 Agent 方式，每个 Agent 拥有独立上下文和明确的研究目标。

**Coding Agent 完成代码修改后，检查代码质量**，一个 Agent 就够了。日常自检可以作为同一流程的一个步骤；需要独立视角时，再按 [4.7](../04-改进机制/4.07-代码Review.md) 的原则引入独立的 review。

**同一个任务分布在不同的工作空间**，建议多 Agent 架构。例如同一个需求的前后端分离、测试与研发分离、PRD 文档与详细设计分离。原因是不同工作空间往往需要不同的上下文、职责边界和执行策略：多 Agent 可以实现职责隔离，每个 Agent 在自己的工作空间内按各自的规范和约定工作；而单 Agent 多 Tools 仍然共享同一个决策中心和同一份上下文，不同工作空间的规则与假设容易互相串扰。这对应 [3.3](3.3-架构选择的判断维度.md) 判断表中"需要独立上下文"和"专业指令明显冲突"两个维度。此时 main-agent 只负责任务分发与跨空间契约对齐（如接口字段、验收标准），不介入各工作空间内部的实现决策。
