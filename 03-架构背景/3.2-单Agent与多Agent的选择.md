# 3.2 单 Agent 与多 Agent 的选择

**优先选择单 Agent 多 Tools 架构。**只有当单个会话已经无法容纳任务，或子任务必须并行且彼此完全独立时，才有必要考虑多 Agent。判断时要综合考察子任务之间的依赖关系、是否可以并行、上下文共享需求、专业边界和执行目标。两者的本质区别有两点：执行形态上，前者是一个 Agent 调用多个工具，后者是多个 Agent 分工协作；决策结构上，前者只有一个决策者，后者有多个。

在单 Agent 多 Tools 架构中，main-agent 是唯一的决策者，工具只承担辅助性工作，这也有助于防止 main-agent 因上下文膨胀而出现上下文腐败。在多 Agent 架构中，main-agent 理解需求后决定交给哪个 Agent，每个 Agent 基于 main-agent 给出的概览进行推理，并各自拥有自己的决策能力。

需要警惕过度设计。中心化的多 Agent 协作（一个 plan，每个模块各由一个 Agent 执行）协调成本高，前后衔接容易断裂；仅因业务领域不同就拆分 Agent，也会把本来可以统一处理的问题切碎。另一个常见误区是，很多 subagent 其实只是把模型本来就能完成的工作单独拆成了一次调用。main-agent 交给 subagent 的往往只是精简后的概览，关键上下文在传递中丢失，子任务质量随之下降；主 Agent 还要额外整合结果。这样算下来，成本往往大于收益。

工具也有两种不同的形态。**原子工具**完成一个明确的操作，形式可以是本地函数、MCP 工具或脚本。**Subagent-as-Tool**由 subagent 封装，完成一个需要多步推理的相对独立的任务（例如阅读并分析一批代码），调用方通常只拿到最终结论。
